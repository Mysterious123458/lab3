# Городские обращения о благоустройстве

Учебное приложение для лабораторной работы 3 по РБПО, вариант 26. Жители оставляют обращения по городским объектам, диспетчер назначает рабочие бригады и закрывает работы. Состояние хранится в PostgreSQL, а не в памяти.

Номер студенческого билета задан в `spring.application.name`: `24074`.

## Предметная модель

- **Пользователь** (`app_users`) — автор обращения. Email уникален.
- **Городской объект** (`city_objects`) — адрес, тип и состояние. Тип: `YARD`, `PARK`, `ROAD`, `PLAYGROUND`, `LIGHTING`. Состояние: `GOOD`, `SATISFACTORY`, `NEEDS_REPAIR`, `EMERGENCY`.
- **Обращение** (`city_reports`) — ссылка на объект и автора, описание, статус (`NEW`, `IN_PROGRESS`, `RESOLVED`, `REJECTED`) и приоритет (`NORMAL`, `HIGH`).
- **Бригада** (`work_crews` и `work_crew_supported_types`) — название, типы объектов, которые она умеет ремонтировать, и лимит одновременно активных нарядов.
- **Наряд** (`work_orders`) — обращение, бригада, срок, статус (`ASSIGNED`, `IN_PROGRESS`, `DONE`, `CANCELLED`) и описание результата.

Связи многие-к-одному: обращение принадлежит одному объекту и одному автору, наряд принадлежит одному обращению и одной бригаде. Типы бригады хранятся отдельной таблицей. Внешние ключи не дают оставить ссылку на удалённую строку. Удаление объекта, пользователя, обращения или бригады в сервисе сначала удаляет зависимые строки.

Время создания и изменения записывает сервер. Пароль базы приложение читает только из переменных окружения.

## Бизнес-операции

Обычные GET, POST, PATCH и DELETE остаются. Закрыть обращение или наряд через них нельзя: финальные статусы ставят только операции ниже. Каждая операция смотрит на текущее состояние связанных записей и либо меняет несколько таблиц в одной транзакции, либо отклоняется.

1. `POST /api/city-reports/{id}/assign` — назначить бригаду. Создаёт активный наряд и переводит обращение в `IN_PROGRESS`. Отказ, если обращение закрыто, наряд уже есть, бригада не работает с типом объекта или у неё исчерпан лимит.
2. `POST /api/work-orders/{id}/complete` — завершить наряд. Наряд становится `DONE`, состояние объекта меняется на переданное. Если других активных нарядов по обращению нет, обращение становится `RESOLVED`. Отказ для уже закрытого наряда и пустого результата.
3. `POST /api/city-reports/{id}/reject` — отклонить обращение и отменить его активные наряды. Отказ, если обращение уже выполнено или уже отклонено.
4. `POST /api/work-orders/{id}/reassign` — передать активный наряд другой бригаде. Отказ, если наряд закрыт, бригада та же, тип объекта ей не подходит или лимит занят.
5. `POST /api/city-objects/{id}/mark-emergency` — отметить объект аварийным и поднять приоритет его открытых обращений до `HIGH`. Отказ, если объект уже аварийный или открытых обращений нет.

## База данных

Сервис подключается пользователем `lab3_app`. У него есть только чтение и изменение строк в таблицах приложения, без права менять схему. Таблицы и учебные строки создаёт администратор скриптом `db/init.sql`.

На этой машине PostgreSQL и Docker не установлены. Дальше один из двух способов.

PostgreSQL 16, установленный локально:

```sql
CREATE DATABASE lab3;
```

Затем в pgAdmin открыть базу `lab3` и выполнить `db/init.sql`.

Либо Docker, из папки проекта, после копирования `.env.example` в `.env`:

```bash
docker compose up -d
```

Перед запуском приложения задать переменные из `.env.example`:

```text
DB_URL=jdbc:postgresql://localhost:5432/lab3
DB_USERNAME=lab3_app
DB_PASSWORD=lab3_app_password
```

Пароли в `.env.example` учебные, для локальной базы. Файл `.env` в репозиторий не входит. Нужен JDK 17 или новее.

```bash
mvn spring-boot:run
```

Приложение слушает `http://localhost:8080`. В таблицах уже есть пользователи, три объекта, две бригады, три обращения и один наряд, поэтому списки можно смотреть сразу.

Запросы для проверки лежат в `postman/lab3.postman_collection.json`: CRUD по каждой сущности и сценарий от нового обращения до назначения бригады, завершения, отклонения, передачи наряда и аварийного статуса.
